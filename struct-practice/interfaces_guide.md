# Интерфейсы и встраивание (embedding) в Go

Гайд на примере проекта `struct-practice` (модуль `yarvinen.ru/struct-practice`)
с типами `Note` и `Todo`.

---

## Часть 1. Что такое интерфейс

**Интерфейс — это набор методов.** Он описывает *что тип умеет делать*, но не
*как*. Конкретный тип (`Note`, `Todo`) описывает реализацию.

```go
type Saver interface {
	Save() error
}

type Printer interface {
	Print()
}
```

`Saver` говорит: «любой, у кого есть метод `Save() error`, является `Saver`».

### Главная фишка Go: реализация **неявная**

В Go **нет ключевого слова `implements`**. Тип реализует интерфейс автоматически,
просто потому что у него есть нужные методы. Это называется *duck typing*:
«если крякает как утка — значит утка».

```go
// note/note.go
func (n Note) Print() { ... }       // есть Print()  → Note это Printer
func (note Note) Save() error { ... } // есть Save()   → Note это Saver
```

Нигде не написано «Note реализует Saver» — компилятор сам это видит. То же самое с
`Todo`: у него есть `Print()` и `Save()`, поэтому он тоже и `Printer`, и `Saver`.

## Часть 2. Зачем нужны интерфейсы (полиморфизм)

Интерфейс позволяет писать функцию **один раз** для разных типов. Смотрите на
`saveData`:

```go
func saveData(data Saver) error {
	err := data.Save()
	...
}
```

Функция принимает **`Saver`**, а не конкретный `Note` или `Todo`. Поэтому одна и та
же функция работает с любым типом, у которого есть `Save()`:

```go
saveData(Note) // ✅ Note — это Saver
saveData(Todo) // ✅ Todo — это Saver
```

Если завтра появится `Reminder` со своим `Save()` — `saveData` будет работать с ним
**без единого изменения**. В этом и сила: код зависит от *поведения* (метод
`Save`), а не от конкретного типа.

> Правило: **принимай интерфейсы, возвращай конкретные типы.** Функции лучше брать
> в аргументы интерфейс (гибко), а конструкторы (`note.New`, `todo.New`) — отдавать
> конкретный `Note`/`Todo`.

## Часть 3. Встраивание интерфейсов (interface embedding)

Интерфейсы можно **собирать из других интерфейсов**. Именно это сделано в `main.go`:

```go
type Outputter interface {
	Saver   // встроили интерфейс Saver
	Printer // встроили интерфейс Printer
}
```

`Outputter` не объявляет своих методов — он **наследует** их из встроенных
интерфейсов. Это полностью эквивалентно записи:

```go
type Outputter interface {
	Save() error // из Saver
	Print()      // из Printer
}
```

Теперь тип является `Outputter`, только если умеет **и** `Save()`, **и** `Print()`.
`Note` и `Todo` умеют оба метода — значит они `Outputter`. Поэтому работает
`saveAndPrint`:

```go
func saveAndPrint(data Outputter) error {
	data.Print()         // метод из Printer
	return saveData(data) // data также годится как Saver
}
```

Обратите внимание: `data` имеет тип `Outputter`, но спокойно передаётся в
`saveData(data Saver)` — потому что `Outputter` **включает** `Saver`.

Самый известный пример из стандартной библиотеки построен так же:

```go
type ReadWriter interface {
	Reader // Read(p []byte) (n int, err error)
	Writer // Write(p []byte) (n int, err error)
}
```

## Часть 4. Встраивание структур (struct embedding) — бонус

Встраивать можно не только интерфейсы, но и **структуры в структуры**. Это способ
переиспользования (композиция вместо наследования).

Допустим, у `Note` и `Todo` есть общие поля. Выносим их в отдельную структуру:

```go
type Base struct {
	ID        string
	CreatedAt time.Time
}

func (b Base) Describe() string {
	return "id=" + b.ID
}

type Note struct {
	Base    // встроенная структура (без имени поля!)
	Title   string
	Content string
}
```

Поля и методы встроенного `Base` **поднимаются** (promotion) на уровень `Note` —
к ним обращаются напрямую, как будто они свои:

```go
n := Note{}
n.ID = "42"          // на самом деле n.Base.ID — но писать можно коротко
n.CreatedAt = time.Now()
fmt.Println(n.Describe()) // метод Base тоже доступен напрямую
```

Ключевое отличие от обычного поля:

```go
type Note struct {
	Base         // ВСТРАИВАНИЕ → n.ID работает напрямую
	meta Base    // ОБЫЧНОЕ ПОЛЕ → нужно писать n.meta.ID
}
```

### Связка двух механизмов

Если встроенный тип реализует интерфейс, то **внешняя структура автоматически тоже
его реализует** — методы ведь поднялись наверх. Удобно для переиспользования общего
поведения.

## Шпаргалка

| Что                       | Синтаксис                          | Что даёт                                  |
| ------------------------- | ---------------------------------- | ----------------------------------------- |
| Интерфейс                 | `type Saver interface { Save() error }` | Описывает поведение                     |
| Реализация                | просто метод на типе               | Неявно, без `implements`                  |
| Встраивание интерфейсов   | `type Outputter interface { Saver; Printer }` | Объединяет наборы методов        |
| Встраивание структур      | `type Note struct { Base; ... }`   | Поднимает поля и методы `Base` в `Note`   |

> Главная идея: интерфейс = «что умеет», встраивание = «собрать из готовых частей».
> В вашем `main.go` обе техники уже применены — `Outputter` собран из `Saver` и
> `Printer`, а `Note`/`Todo` реализуют их неявно.
